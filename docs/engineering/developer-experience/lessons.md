# Lessons Learned

## Hidden coupling: TTL guards poisoned by mass operations

- The floor-switch "all tables available" regression: `_patchSessionsFromTables` cleared OTHER plans' sessions on every plan-scoped snapshot patch (wrong authority scope), and each CLEAR fed `recentlyClearedSessions` (a 30s TTL guard meant for real table clears). The TTL map then made `fetchFloorPlanSnapshot` strip those sessions from every fresh fetch — so making fetches MORE frequent (prefetch re-warm) surfaced a latent state-destruction loop.
- Pattern: a "recently X" TTL guard is only sound if X is recorded ONLY for genuine X events. Before adding/refreshing any fetch path, grep for guards that filter its output (`wasRecently*`, suppress windows) and check what feeds them.
- Snapshot patch functions must match the snapshot's authority scope: a plan-scoped fetch may only clear state for tables IN that plan.

## Native code in "JS" dependencies

- Never claim a new dependency needs no dev-client rebuild without checking for an `android/` or `ios/` directory in its package. `@shopify/flash-list` v1 looks JS-only (RecyclerListView heritage) but ships native views (`AutoLayoutView`, `CellContainer`) — old dev clients throw "View config not found".
- Check: `ls node_modules/<pkg>/android` or look for `codegenConfig`/`RN podspec` in its package.json. If native code exists: `npm run android` rebuilds for emulator; Landi needs a fresh EAS development build.
- ~~FlashList v1 on New Architecture: native `AutoLayoutView` can misdraw a dark rectangle over viewport space below short content. Use `disableAutoLayout` for uniform-cell grids.~~ **Wrong on both counts — reverted.** The dark rectangle was a themed `backgroundColor` frozen into `StyleSheet.create` at module load (the `colors` Proxy defaults to dark), not `AutoLayoutView`; fixed properly in 0b748ad1 by applying the background inline. And `disableAutoLayout` is never safe as a blanket setting: it disables `clearGapsAndOverlaps`, the only in-frame corrector for cells drawn at stale offsets, which later surfaced as menu tiles overlapping on menu switch. Only set it when you supply a custom `CellRendererComponent` (the one case the FlashList docs list).
- FlashList v1 sizes grid rows from a running `AverageWindow` of **measured** cell heights (`GridLayoutProviderWithProps.reportItemLayout`), not from `estimatedItemSize` — that value only seeds the window, and the average carries across layout managers. So any zero-height cell permanently drags the row pitch down for every list that follows. Never pad a FlashList grid's last row with filler items the way you would a FlatList: `GridLayoutProvider.setLayout` already fixes each cell's width at `containerWidth / numColumns * span`, so a partial last row lays out correctly on its own.
- Debugging visual layout remotely: `adb exec-out screencap -p` + `adb shell uiautomator dump` (view bounds) + `adb shell input tap` against the running emulator beats guessing from cropped screenshots — the UI dump showed the list viewport was sized correctly, isolating the bug to the native overlay.

## Order Lookup Patterns

- `getOrder()` alone is fragile for DraggableTable — `dbOrderIdIndex` has timing gaps after seating
- Sidebar (`TableListItem`, `SeatedPanel`) already uses resilient fallbacks (scan by `service_location_id` or `db_order_id`)
- When multiple components need the same data, ensure they all have equivalent resilience — don't let one component use a weaker lookup strategy

## Supabase RPC Schema Checks

- Before adding column assignments inside SQL RPC migrations, verify the target table columns in `database.types.ts`; `kds_item_status` does not have `updated_at`.

## Workflow / subagent isolation

- Workflow (and Agent-tool) subagents share the MAIN working tree unless launched with `isolation: 'worktree'`. A read-only-intended Explore agent still has Bash and CAN run `git checkout` — one did, silently switching the shared tree from `feat/pos-menu-surface` to `Table-And-Order-Syncing` mid-run. Nothing was lost (tree was clean) but it's disruptive.
  - Fix going forward: when a workflow's agents will touch git or read from a specific branch, either (a) set `isolation: 'worktree'`, or (b) instruct them explicitly to use `git show <branch>:<path>` (never `checkout`), and re-assert "do not switch branches." Always restore the user's original branch afterward.
- Squash-merged PRs: the local feature-branch commit (e.g. `fix/sync-order-from-database-rpc` @ 959c4739) is NOT an ancestor of the integration branch after a GitHub squash-merge (which creates a fresh commit, e.g. 509cc7c1). To get the post-merge code locally you must `git fetch`; `git branch --contains <mergeSha>` returns empty until then. Base fast-follows on `origin/<integration-branch>` after fetching.

## Replacing native modal sheets with in-tree JS overlays (PanelSheet)

- The app routes every sheet through `components/ui/bottomSheet.tsx` → `@expo/ui/community/bottom-sheet`, which on Android is a Material3 `ModalBottomSheet` — a screen-level **dialog window**. That window (a) doesn't inherit the app's hidden/immersive status bar → opening any sheet re-reveals the status bar and shifts the edge-to-edge UI, and (b) always centers at a 640dp max width → can't anchor to a sub-column. Neither is fixable from JS props (`ModalBottomSheetView.kt` only exposes `shouldDismissOnBackPress`/`shouldDismissOnClickOutside`). To anchor a sheet to a sub-region without the status-bar shift, it must be an in-tree JS overlay, not the native sheet. `PanelSheet` (`components/ui/PanelSheet.tsx`) is that overlay for the four bill-panel sheets; the shared adapter stays for the ~40 other sheets.
- **Animating a wrapped `Pressable`'s opacity is unreliable.** `Animated.createAnimatedComponent(Pressable)` with an animated `opacity` style renders once at the initial value and never updates — so a backdrop built that way stays invisible (opacity frozen at 0) even though a sibling `Animated.View`'s `translateY` animates fine. Fix: dim with a plain `Animated.View` (`pointerEvents="none"`) and put a separate transparent `Pressable` behind it for tap-to-dismiss.
- **Anchor overlays via the root `PortalHost`, not the local sheet-mount container.** `order-processing.tsx`'s `sheetOverlayLayer` is `absoluteFill` + `top: -overlayHeaderHeight` inside a `px-2 py-1` padded parent; an absolutely-positioned child inherits that shift/padding, so `bottom:0` doesn't land at the true screen bottom and the panel mis-sizes/mis-docks. Rendering through `@rn-primitives/portal` `<Portal>` (single default `<PortalHost/>` at `app/_layout.tsx:994`; the `(main)/_layout` one is named `profile-overlay`) puts the overlay in clean full-screen coordinates. Publish the target column's `{width,height}` via a tiny store (`useBillPanelLayoutStore`, written from the column root's `onLayout`) and size the panel to it.
- Jest gotchas hit here: the global `react-native-reanimated` mock in `jest-setup.ts` crashes on import (pulls in real `react-native-worklets`) — override with a self-contained mock in the test file; `@testing-library/react-native` v14 can't resolve its `test-renderer` (existing component tests are already red) — use `react-test-renderer` + `act` directly; `@rn-primitives/portal` ships untransformed JSX not in `transformIgnorePatterns` — mock `Portal` as a passthrough in the test. `withTiming`'s completion callback fires synchronously under the reanimated mock, so callback-driven close→onClose is testable without timers.

## Fixes silently reverted by big unrelated merges

- The single-cent payment guard regressed **twice**: shipped in `40dee0fd` ("feat: updated support for single cent payments"), then clobbered 2 days later by `90f0ed1e` ("Jaffal bug fixes #134") — a large void/broadcast refactor that had nothing to do with payments but reintroduced the old `isFinalSplitPortion` / `forceExplicitAmount`-gated `<= $0.01` guard in `addPaymentToOrder`. Symptom: a $0.01 card purchase approves on the pinpad but the POS shows "No unpaid items" and the order stays awaiting payment (the terminal charges BEFORE `addPaymentToOrder`, which then `return false`s at the guard and never calls the RPC).
- The penny-guard predicate now lives in `lib/paymentGuards.ts` (`isNothingLeftToCollect`) with `__tests__/paymentPennyGuard.test.ts` — a pure function + unit test so a third silent revert fails CI instead of shipping. Backend `process_payment_v16` already tolerates a $0.01 balance (only rejects when `v_payment_based_due <= 0`), and the full-pay flow passes `itemAllocations` so the downstream `itemsCovered.length === 0` guard doesn't fire — the client guard was the sole blocker.
- Pattern: when restoring a bug fix, check WHY it disappeared. `git log -S "<unique-token-from-the-fix>" -- <file>` shows the commit that added it AND the one that removed it. If a subtle, hard-to-integration-test predicate keeps regressing via unrelated merges, extract it to a pure helper with a test rather than re-inlining it.

## Fast-typing duplicates/merges chars in a search bar (item search)

- Symptom: typing fast in an item search bar produces duplicated/concatenated text. Root cause is NOT an append-style `onChangeText` — it's a heavy **synchronous filter on the keystroke critical path**. The item-search sheets (`components/menu/SearchBottomSheet.tsx` — the sales/order-processing "Search menu…", and `components/menu/MenuSearchSheet.tsx` — menu management) each run a `useMemo` that filters the ENTIRE menu (~2000 items → sections → flattened rows) on every keystroke, in the same component that owns the controlled `BottomSheetTextInput`. That per-keystroke JS-thread stall lets the controlled input's `value` commit lag the native keystroke buffer on Android/Fabric, so RN re-applies text → duplication/merge.
- Fix (React 19): `const deferred = useDeferredValue(searchText)` and feed the DEFERRED value to the expensive filter `useMemo` (and its dep array), while the `<TextInput value={searchText}>` stays bound to the RAW state. The urgent keystroke render then only updates the cheap input (filter memo deps unchanged → cached, no work); React re-runs the filter in a later interruptible pass. No debounce timers, no new components, results stay as fresh as the device can render. Empty-state text / clear button keep using the raw value (instant).
- Process lesson: "sales" is ambiguous in this app — the order/sales-history screen (`previous-orders.tsx`, "Sales" history) vs the sales/order-*building* screen (`order-processing.tsx`, where you search menu items to ring up a sale). I first fixed the wrong one (previous-orders history search) before the user clarified "item search bar." When a colloquial screen name maps to multiple search bars, confirm the exact element (or which flow) before implementing.

## Auto UI-scale formulas must match the screen's orientation, not the baseline's

- `computeKioskUiScale` scored a portrait kiosk against a **landscape** baseline (1333×752 dp): a 1080×1920 panel compared its 1080 width to 1333, `Math.min(widthRatio, heightRatio)` picked that 0.81, and a 32" kiosk rendered *smaller* type than a 10" tablet. Every kiosk component looked "too small on big screens" and the instinct was to bump font sizes component-by-component — the actual fix was one formula: compare short-edge to short-edge and long-edge to long-edge, which doubled the scale (0.81 → 1.61) with zero component edits.
- Pattern: when a whole surface reads as mis-sized, check the scale function **before** touching individual sizes. A ratio-vs-baseline formula is only valid while both operands share an orientation; the moment a route can rotate (kiosk portrait lock, foldables, split-screen), axis-to-axis comparison is a bug.
- Corollary: derive per-component sizing from a measured local dimension (menu card width) rather than the global scale where the component's size also depends on a user setting (items-per-row). One input then covers screen size *and* the setting, and clamps only need to catch true extremes — but set those ceilings above what the global scale cap can produce, or card type stalls while the surrounding chrome keeps growing.
- Any component using raw `px` silently opts out of the scale entirely. `KioskIdleModal` (fontSize: 28/16/18, no `kioskPx`) was the one surface a customer has seconds to read before their order is voided, and it was the smallest thing on the screen.

## Raising a global UI scale breaks every layout whose bound is a multiple of that scale

- After fixing `computeKioskUiScale` (0.81 → 1.61 on a portrait kiosk), the item-detail photo in **landscape** broke. Its box was `width:"100%" + height:"100%" + aspectRatio:1`, bounded only by `maxHeight: kioskPx(440, s)`. That cap is a multiple of the scale, so it grew straight through the panel — while the title block's type grew too — putting the column 107–207px over the available height on *every* panel size. RN doesn't shrink by default, so the photo blew out of its box and fought the aspectRatio constraint.
- Two compounding smells: (a) `width:100% + height:100% + aspectRatio:1` is over-constrained — Yoga has to discard one, so it distorts rather than clipping; (b) a "max size" expressed in scaled px is not a bound at all when the thing it must fit inside is a fraction of the *screen*.
- Fix that generalises: when a child must fit whatever a sibling leaves over, don't compute its size from a fraction of the viewport — put it in a `flex: 1` box and inscribe it in the box's **measured** dimensions (`onLayout`, one state var, conservative first-frame estimate so it only grows into place). Self-correcting for any panel size and any length of copy, with no factor to re-tune. Applies equally to the portrait hero, which also needed a *width* bound: a third of a tall/narrow panel's height (800×2560) exceeds its full width.
- Checklist when changing a global scale: grep the touched surface for `maxWidth`/`maxHeight`/fixed `height` expressed through the scale helper, and for any `100%`+`aspectRatio` pair. Those are exactly the places a scale increase turns into an overflow.

## A grid card sized from width alone breaks on short, wide viewports

- Kiosk menu cards derived every dimension from measured **card width** — correct in portrait, where width is the scarce axis. In landscape the grid is wide and short, so dropping to 2 columns made each card 673px wide, a width-derived image 485px tall, and one row 863px of an 874px viewport: **1.01 rows visible**, a single row of two enormous cards with 64px type. Fix: pass the grid's measured **height budget per card** alongside width, cap the image against it, and derive type from `min(width, budget × k)` so a wide-but-short cell doesn't get billboard type just because it is wide. Keep purely horizontal affordances (show-description, line counts) keyed to real width.
- Past a width:height ratio of ~1.4 no top-image card works — the photo can only fit by letterboxing. That's a signal to change the card's *shape*, not its size: rotate to image-left/copy-right. Worth checking whether such a component already exists before writing one; ours did, sitting unused with a stale doc comment claiming a template used it.
- Verification technique that paid off repeatedly here: a throwaway Node script that replays the whole sizing chain (screen dp → UI scale → rail % → card width → metrics → card height → **rows visible**) across a matrix of panels × column counts. "Rows visible" is the number that actually exposes the bug; card width and font size both look reasonable in isolation. Kept the invariants as unit tests afterwards.

## Greying out an unavailable choice is a POS affordance, not a customer one

- Kiosk modifier options with `isAvailable === false` rendered at 0.4 opacity and untappable. Worse, a **required** group with every option 86'd was a hard dead end: nothing selectable, so its entry in `missingRequired` never cleared, `canAdd` stayed false, and the CTA read "Select <group>" forever — the item could not be ordered and the customer could only back out. Staff need to see what the kitchen is out of; a customer can only be confused by a choice they aren't allowed to make.
- Fix in two layers: hide unavailable options and drop emptied groups in the shared hook, AND hide the item from the menu entirely when a required group has nothing available (plus the category, if nothing in it is orderable — otherwise hiding items just moves the dead end to an empty grid). Availability predicates should fail **open**: an item whose modifier groups can't be resolved yet stays visible, because hiding a sellable item over a hydration gap is worse than showing one the detail screen will handle.
- Also check default pre-selection when adding an availability filter — ours seeded from `isDefault` without checking `isAvailable`, so an 86'd default was being pre-selected into the cart line and sent to the kitchen.
